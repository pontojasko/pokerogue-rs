# Architecture map

Original checkout: `original/`, pinned to `7c0881255af5cd51992e513ff93c2f71adbe40e0` of pagefaultgames/pokerogue. It is a TypeScript/Vite/Phaser 4 project; `src/field/pokemon.ts` owns Pokémon stats and attack damage, `src/data/moves/move.ts` declares moves and accuracy, `src/phases/move-effect-phase.ts` checks hits, `src/battle.ts` owns the battle RNG stream, and `src/utils/common.ts` owns shared seeded RNG helpers. Tests are Vitest under `test/tests`, with focused damage and battle suites. The required asset files are a sparse local checkout; no network is needed to run the Rust client.

Original `getBaseDamage` uses `((2 * level / 5 + 2) * power * attack / defense / 50) + 2`; `getAttackDamage` applies multipliers including a 0.85–1.00 random factor, STAB, type effectiveness, crit, weather, and battle modifiers. Move declarations for Tackle and Ember are in `src/data/moves/move.ts` (both power 40), and Vine Whip is power 45. This first slice implements base formula, STAB, and a seeded 0.85–1.00 roll. It uses Bulbasaur and Charmander base stats from `src/data/balance/species/generation-01.ts`, at level 5 with IV 0 to keep a deterministic fixture. Core is independent of Macroquad; data is separated; tests-facing integration crate depends on core/data only. Assets are not reused until their submodule license metadata is reviewed.

Migration order: (1) deterministic battle foundation and focused parity fixtures; (2) automated species/move data import from the pinned source; (3) phase-accurate battle completion; (4) first wave/encounter loop; (5) experience, levels and basic rewards; (6) local saves; (7) first offline mini-run. See `ROADMAP.md` for objective completion criteria and `PARITY_PLAN.md` for evidence and gaps.

Sprite prototype: Macroquad reads Bulbasaur back and Charmander front atlases from `original/assets/images/pokemon` (or `POKEROGUE_ASSETS_DIR`). The upstream `images/pokemon/{1,4}.json` atlas metadata specifies the source rectangles; frame 0001/0003 are used for a two-pose idle loop. Files are kept in the local upstream checkout because their exact redistributability is unresolved; see `ASSET_CREDITS.md`.

Battle slice fidelity update: `pokerogue-data/src/type_chart.rs` is generated by `scripts/extract_type_chart.mjs`, which executes the exact `getTypeChartMultiplier` function body extracted from `original/src/data/type.ts`. `pokerogue-tests/fixtures/type-chart.csv` covers all 18×18 regular type pairs. Core multiplies effectiveness across both defender types, returns zero before damage minimum for immunities, applies STAB when either attacker type matches, and uses original move categories (Ember is special) and powers (Vine Whip 45, Tackle/Ember 40). Damage multiplication order and floor/minimum follow `getAttackDamage` and `toDmgValue` in `original/src/field/pokemon.ts` / `original/src/utils/common.ts`. One deterministic Tackle damage case also matches the explicit expected result in `original/test/tests/battle/damage-calculation.test.ts`. Ability, item, move-attribute, weather, critical, accuracy, and exact battle RNG behavior remain out of scope.

Accuracy/RNG slice: core ports Phaser 4.2.1 `RandomDataGenerator` (Alea hash/state/frac/range calls), plus PokéRogue's `shiftCharCodes(battleSeed, turn << 6)`, state carry within a turn, and reset each turn. `accuracy_multiplier` implements the unmodified ACC/EVA stage ratio; move accuracy is checked as `rand(0..99) < baseAccuracy * multiplier`, after type immunity and before damage RNG. Current three moves have 100 accuracy; no weather, accuracy abilities/items, variable-accuracy attributes, semi-invulnerability, or accuracy bypass tags are modeled. Battle demo uses a fixed seed for offline reproducibility. See `PARITY_PLAN.md` for validated and partial parity details.

Runtime boundary: the core and data crates have no Macroquad dependency; the client owns Macroquad input/rendering and reads local assets. Runtime has no network/API/Node dependency. Future local saves/config should use a separate persistence layer. R36S preparation remains a portability constraint only (RK3326 Cortex-A35, 1 GB RAM, 640×480 Linux/ArkOS; userspace bitness and Macroquad support are not assumed).

## Moveset/save storage note

The battle core stores four move slots per battler. Version 22 local checkpoints preserve slot count, move IDs, PP use, PP Ups, and used-TM history for each party member while retaining readers for v4–v21 (v21 stored four move slots without used-TM history). Macroquad presents the active slots; move learning and party choices remain core operations.


Visual tooling: `tools/visual/` owns development-only local Phaser/Playwright fixtures and source harness; `scripts/visual_parity.py` orchestrates readback, PNG comparison and reports. `pokerogue-client/src/visual.rs` owns the fixture-only presentation clock/state loader and internal framebuffer export, leaving core/data rules untouched. Node/Playwright/ImageMagick are not runtime game dependencies. See `tools/visual/README.md` for the bounded reference and verified local capture/regression gates.


`pokerogue-client/src/hud.rs` loads source HUD atlases/font at runtime from the local pinned checkout and draws ratio-selected HP frames, level/HP sprites and labels. `tools/visual/ui-source.mjs` transpiles the actual original HUD/text classes with disclosed hidden collaborators; the native renderer does not depend on this development harness. `scripts/visual_suite.py` orchestrates six real scenarios and explicit ignored local baselines. Native capture can own an ephemeral Xvfb server, preserving normal gameplay/display configuration.
